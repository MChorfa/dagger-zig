# dagger-zig v1.0 Roadmap

This page tracks the path from the current `v0.3.x` releases to `v1.0`, when
dagger-zig will be proposed as a Dagger Community SDK.

## What v1.0 means

`v1.0` is the first release that is **Community SDK-ready**: a stable, documented,
tested Zig SDK that can be listed alongside the official Dagger SDKs and supported
by the community. It does **not** mean every experimental feature is complete.

For Dagger's SDK classification, see [Dagger Community SDKs](https://dagger.io/community-sdk/).
The maintainer requirements are:

| Requirement | v1.0 implication |
| --- | --- |
| Active community support | Maintainer presence in Dagger Discord / GitHub discussions |
| Version compatibility | SDK stays current with Dagger engine releases within one release cycle |
| Documentation maintenance | Getting Started, examples, API reference, and migration docs are current |
| Openness to contributions | Clear `CONTRIBUTING.md`, issue labels, and good first issues |

## 1.0 exit criteria

These must all be true before the `v1.0.0` tag is cut:

- [ ] Core client API has parity with the Go/Python/TypeScript SDKs for the
      built-in Dagger types (Container, Directory, File, Secret, Service,
      CacheVolume, Platform, Module, Function).
- [ ] Module authoring supports the Dagger `ModuleRuntime` contract end-to-end,
      including `dagger call` for all exposed functions.
- [ ] CI runs `zig build test`, `test-module`, `test-suite`, and
      `test-integration` green on Linux, macOS, and Windows.
- [ ] Release pipeline produces SBOMs, SLSA L3 provenance, and Sigstore
      signatures automatically.
- [ ] Documentation covers Getting Started, Module Authoring, Build Guide,
      Compliance, and a v1.0 migration note.
- [ ] A v1.0-compatible `build.zig.zon` dependency pattern is documented and
      pinned for reproducible fetches.
- [ ] No `error.NotImplemented` paths are reachable through the documented v1.0
      public API.
- [ ] The Dagger Community SDK process has been started (email
      `community@dagger.io`).

## Phases

### Phase 0 — Stabilize the v0.3.x baseline

Goal: the project is a reliable daily driver for POSIX users.

| Item | Why it matters | Owner | Target |
| --- | --- | --- | --- |
| Fix remaining `error.NotImplemented` in the public API | v1.0 cannot ship unreachable code paths | — | v0.3.7 |
| Resolve Windows `dagger run --` and path handling gaps | CI parity; `platform.zig` already has conditional logic that short-circuits on Windows | — | v0.3.7 |
| Harden the self-hosting CI pipeline (`ci/pipeline`) | Release provenance and docs builds must be green before v1.0 | — | v0.3.7 |
| Complete `docs/` consistency pass | Community SDK documentation requirement | — | v0.3.7 |

### Phase 1 — Feature parity and test coverage

Goal: the SDK can do everything the official SDKs do for the standard types.

| Item | Why it matters | Owner | Target |
| --- | --- | --- | --- |
| Audit `sdk/lib/src/gen.zig` against Dagger `v0.21.x` schema | Catch any missing scalar or object types | — | v0.4.0 |
| Add `dagger call` integration tests for the e2e module | Proves module authoring works for consumers | — | v0.4.0 |
| Expand `test-suite` coverage for query builder, serialization, and tracing | Confidence in the public API | — | v0.4.0 |
| Add Windows to the integration test matrix | Prevents regressions on the non-POSIX path | — | v0.4.0 |

### Phase 2 — Windows and C ABI

Goal: remove the "Planned" label from Windows and make the C library usable.

| Item | Why it matters | Owner | Target |
| --- | --- | --- | --- |
| Finish `platform.zig` Windows transport paths | `connect()` and CLI discovery currently return `!is_windows` | — | v0.5.0 |
| Stabilize `zig build c-lib` and header generation | Enables C/Python/Rust consumers | — | v0.5.0 |
| Add Windows-specific examples and docs | Required for Community SDK parity | — | v0.5.0 |

### Phase 3 — Release and community readiness

Goal: the project behaves like a Community SDK, not a personal repo.

| Item | Why it matters | Owner | Target |
| --- | --- | --- | --- |
| Cut release candidates (`v1.0.0-rc.1`, etc.) | Bake time and downstream testing | — | v0.5.x |
| Open the Dagger Community SDK application | `community@dagger.io` with the checklist in hand | — | v1.0.0-rc.1 |
| Create a `v1.0` migration guide | Users upgrading from `v0.3.x` need a short changelog | — | v1.0.0 |
| Tag `v1.0.0` and write release notes | Public signal that the SDK is stable | — | v1.0.0 |

## Out of scope for 1.0

These are intentionally **not** part of the v1.0 gate. They can land in `v1.x`
releases without breaking the Community SDK proposal.

- **Native SPIFFE Workload API** — the shellout backend supports X509 fetch; the
  native gRPC Workload API remains experimental and incomplete.
- **Per-module code generation** — consumers use the engine's schema-driven codegen.
- **Advanced telemetry** — tracing is present, but metrics and dashboards are not.

## Risks and open questions

| Risk | Mitigation | Status |
| --- | --- | --- |
| Dagger engine API churn between `v0.21.x` and a future 1.0 | Pin to `v0.21.x` for v1.0; follow engine releases in `v1.x` | Open |
| Windows CI time and availability | Use `windows-latest` in GitHub Actions with short-path checkout | Open |
| Maintaining Zig 0.16 vs 0.17 compatibility | Lock v1.0 to 0.16; bump in a minor release | Open |
